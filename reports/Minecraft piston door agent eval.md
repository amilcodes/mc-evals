# Piston doors can benchmark frontier agents

The idea works, and nothing occupies the slot: the research found exactly one redstone benchmark for LLM agents (SciCrafter, April 2026), and it uses lamps and wire with no pistons, no size score and no human records ([SciCrafter](https://arxiv.org/html/2604.24697v1)). The ingredients for a piston-door eval already exist: a formal community ruleset with a size-record convention ([Squid Rules](https://github.com/redstone-squid/Redstone-Squid/blob/master/reference/Door_Rules.md)), and a headless test runner inside Mojang's own server jar ([Minecraft Wiki: GameTest](https://minecraft.wiki/w/GameTest)). The naive design needs five corrections. First, "seamless" means no circuitry visible from inside the hallway, in tiers, and non-seamless doors are not eligible for community records. Second, size is the bounding-box volume of the circuitry swept over every state of the door, which is close to your first idea, while block count is ranked nowhere. Third, every headline record from 3x3 up uses entity exploits, and the 6x6 and 7x7 records take over an hour to open, so the benchmark should define an entity-free, time-capped category and normalise against the matching sub-records (56 blocks at 3x3, 132 at 4x4, 504 at 5x5) rather than 55, 99 and about 200. Fourth, only Mojang's code simulates pistons faithfully; the fast redstone simulators do not implement them. Fifth, an agent with a callable scorer is the setting where reward hacking has been measured at its highest, so the final verdict must come from an isolated referee. Three caveats run through everything below: the record figures are builders' self-reports that were not checked against the community's own record log, no simulator throughput was measured, and no one has measured a 2026 frontier model on a piston door.

A note on reading this report: a statement followed by a linked source is something the researchers read in that source. A statement introduced as an inference or a recommendation is the research team's reasoning, and no source makes it directly.

## One lamp-circuit benchmark exists, and no piston-door eval

Minecraft evals for LLM agents cluster around survival and tech-tree progress, crafting, blueprint-following or aesthetic building, and collaboration. Building benchmarks score similarity to a blueprint, rule-based structural properties, a learned judge or human votes; none scores whether a mechanism functions and how small it is ([MineCollab](https://arxiv.org/abs/2504.17950), [MineCEraft](https://arxiv.org/html/2608.28884v1), [MineBench](https://github.com/Ammaar-Alam/minebench)). The single exception on function is SciCrafter, which asks agents to light 4 to 64 lamps from one button press using only a button, wire, repeaters, torches, lamps, stone and glass. It records every lamp's state each game tick and passes or fails with a one-tick tolerance. **Unaided frontier models scored 21 to 26%**, and none solved the top level even with oracle hints; its authors write that "explicit benchmarks for redstone reasoning remain limited" ([SciCrafter](https://arxiv.org/html/2604.24697v1)).

The researchers infer that the proposed eval is new on four axes relative to SciCrafter: moving blocks and piston mechanics, a continuous compactness score, normalisation against human records, and a long open-ended iteration budget. Targeted searches found no piston-door solver, no genetic or SAT search over doors, and no systematic record of 2026 frontier models attempting one; the nearest items are a January 2026 SAT encoding of dust, torches and blocks, and two 2026 hobby projects that pair coding agents with tick-exact redstone tests ([alloc.dev](https://alloc.dev/2026/01/09/redstone_from_sat), [schemsmith](https://github.com/syrianah/schemsmith/issues/16), [mscts](https://github.com/ericbstie/mscts/issues/40)). Absence from web search is not proof of absence, and community tools that live only in Discord would not have surfaced.

The design pattern, by contrast, is mature. RE-Bench scales scores so that a provided starting solution is 0 and a reference solution is 1, lets agents call the scorer at will, and compares against 71 eight-hour expert attempts ([RE-Bench](https://arxiv.org/html/2411.15114)). ALE-Bench and CodeGolf Bench rank agent output against an existing human competitive community ([ALE-Bench](https://arxiv.org/html/2506.09050v2), [CodeGolf Bench](https://arxiv.org/pdf/2605.30394)). The Factorio Learning Environment exposes a deterministic engineering game as a Python REPL, and its authors still list human baselines as future work, a gap piston doors do not have ([FLE](https://arxiv.org/html/2503.09617v1), [FLE v0.3](https://jackhopkins.github.io/factorio-learning-environment/versions/0.3.0.html)). Karpathy's autoresearch loop supplies the "auto-research" template you describe: one editable artefact, one scalar metric and a fixed budget per experiment ([autoresearch](https://github.com/karpathy/autoresearch)).

The domain also fits published guidance on frontier evals. Anthropic's guidance favours deterministic code graders that grade the output rather than the path, and warns that an eval at 100% gives no signal for improvement ([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). A size score has no ceiling short of the physical minimum. Frontier scores on static Minecraft building sat at 26 to 41% in 2025 and 2026 papers, so the researchers infer the eval will not launch saturated ([MineAnyBuild](https://arxiv.org/html/2505.20148v3), [MineCEraft](https://arxiv.org/html/2608.28884v1)). One single-source counterweight: a Vals AI page updated in October 2026 reports top models at about 91% on a 30-mission Kerbal Space Program ladder, which suggests late-2026 models are much stronger at code-mediated game engineering than the older papers imply ([Vals](https://www.vals.ai/benchmarks/time_horizon_index)). Difficulty for piston doors must be measured, not assumed.

## Community rules correct the naive design in five places

### Seamless is a hallway-visibility rule with tiers

The Redstone Squid ruleset is the one formal, actively maintained standard. It defines a piston door as an entrance whose hallway is horizontal or vertical and can continue past the wiring indefinitely, with exactly one input device. Seamless means that the hallway shows no circuitry, judged from inside it, in four tiers (super, full, semi, quart) defined over five conditions: the front of the closed door, the open state, the closed state, and the two transitions ([Squid Rules](https://github.com/redstone-squid/Redstone-Squid/blob/master/reference/Door_Rules.md)). The simplified community guide states the two tiers that matter: **full seamless shows no redstone once the door has finished opening or closing, and semi seamless holds in only one of those states** ([Rules for Dummies](https://docs.google.com/document/d/1a0xI0Pj6lKlULCmVr9n4GH2jnpjDXal4HeiJGhzRF0s/edit)). "Flush" and "hipster" are separate axes about where circuitry sits relative to the outer wall or floor.

Two consequences follow for your categories. The researchers recommend that the seamless track be "full seamless NxN regular door, no entities", which is what a headline "smallest NxN" means once entities are excluded. And because a build must reach at least one seamless tier to hold any Squid record, a "non-seamless smallest NxN" is not an officially tracked category; that reading is the researchers' inference from the eligibility rule ([Squid Rules](https://github.com/redstone-squid/Redstone-Squid/blob/master/reference/Door_Rules.md)). Keep the non-seamless track as an easier rung, but normalise it against benchmark-owned baselines, not community records. One caveat: the exact cell values of the four-tier table were images in the source and were not read, so the full-seamless definition should be confirmed with the Squid maintainers before it is frozen.

### Size is swept circuitry volume, and block count is unranked

Your first instinct is close to the community's. Squid volume is width times height times depth of the circuitry's axis-aligned box, **measured cumulatively across both rest states and every opening and closing motion**, with entities counted. Door blocks, plain hallway blocks, the frame, outer-surface blocks and the input device are excluded ([Squid Rules](https://github.com/redstone-squid/Redstone-Squid/blob/master/reference/Door_Rules.md)). That exclusion list covers your "tunnel that covers the door". The Minecraft Wiki uses the same idea, a box containing the door with empty cells counted ([Wiki: Piston uses](https://minecraft.wiki/w/Tutorial:Piston_uses)).

The naive version is wrong in one place and weak in another. A static bounding box of the closed build under-counts, because pistons and blocks that poke out mid-animation count in community practice; the grader must take the union over every tick. Block count is not a ranked metric anywhere in the ruleset. The notes found no source that compares the two metrics directly, so the recommendation rests on reasoning: use bounding-box volume as the primary score because it matches the records and is unambiguous, and report block count, open and close time in ticks, and reset time as secondary figures, not as a weighted composite. Block count rewards sparse layouts and breaks comparability with every human record. Builders do quote "density", and the 308-block 6x6 has four air cells in its whole box, which shows how tightly volume already forces packing at the frontier ([Cwee 6x6](https://www.youtube.com/watch?v=1Ojxa1Ljj_8)).

### Headline records rely on entities and take hours to open

Since 2022 the unrestricted records from 3x3 up use entity techniques: minecart stacks, mobs, frozen fireballs and carts with broken motion values. The 6x6 record uses 71 entities and takes about 1 hour 20 minutes to open; the 7x7 uses 75 and takes about 1 hour 47 minutes ([Cwee 6x6](https://www.youtube.com/watch?v=1Ojxa1Ljj_8), [Cwee 7x7](https://www.youtube.com/watch?v=ipAx9-AOng4)). These doors are fragile: the 55-block 3x3 broke when a 1.21.11 snapshot removed the cart exploit, and several records do not work on Paper servers ([Door_Maker](https://www.youtube.com/watch?v=dxcZcYBB75s), [Cwee 4x4](https://www.youtube.com/watch?v=AUVLmzOYXFU)). Even the entity-free 6x6 at 360 blocks needs about 1 hour 34 minutes, which is over 100,000 game ticks per opening ([Cwee 6x6 no entities](https://www.youtube.com/watch?v=VZhG8DUL2L8)).

The Squid rules require only that opening and closing have a bounded duration, so nothing in the community standard stops an agent from trading hours of sequencing for volume ([Squid Rules](https://github.com/redstone-squid/Redstone-Squid/blob/master/reference/Door_Rules.md)). The researchers recommend two rule changes for the benchmark. Ban entities, which matches the community's NO ENTITIES restriction (block entities such as hoppers remain allowed under that tag). And cap open and close time, which the community does informally through hybrid titles such as "smallest 0.6 s 3x3 (72 blocks)" ([JensundLars](https://www.youtube.com/watch?v=R6e__lLvwrg)). The cap also bounds grading cost. The exact value is a decision to take in Phase 0, because it selects the reference record at each size.

### Behaviour depends on version, position and orientation

Record doors are Java-only because they depend on quasi-connectivity, sticky pistons dropping blocks on short pulses, and deterministic sub-tick ordering ([Wiki: Quasi-connectivity](https://minecraft.wiki/w/Tutorial:Quasi-connectivity), [Wiki: Zero-ticking](https://minecraft.wiki/w/Tutorial:Zero-ticking)). Records quote narrow version windows, and Mojang's opt-in Redstone Experiments pack changes wire update order and, by Mojang's own statement, affects quasi-connectivity contraptions ([Snapshot 24w34a](https://minecraft.net/en-us/article/minecraft-snapshot-24w34a)). The benchmark must pin one exact Java version and state that the experimental pack is off.

Community technical documentation describes the order of block updates when a piston moves blocks as locational, and record builders advertise "not locational and not directional" as a feature ([TechMC Docs: Piston](https://techmcdocs.github.io/pages/Blocks/Piston/), [Cwee 108b 4x4](https://www.youtube.com/watch?v=Fd-p6AA3syg)). The researchers infer that a fixed build at a fixed position and orientation behaves the same on every run, with no randomness in dust or pistons while the experimental pack is off; that claim was not verified against the 26.x source. In the Squid rules those are opt-in tags, not eligibility gates. The two research strands disagree here. The infrastructure notes recommend one pinned position and facing for the official verdict, with rotations and translations as a secondary robustness score. The anti-gaming notes recommend hidden offsets and rotations to stop agents special-casing the test position. The recommendation is to follow the community: score the headline at one published position and orientation, report the pass fraction across four rotations and several translations as a "not locational or directional" tag, and put the hidden checks into cycles and input timing instead.

## Only Mojang's own piston code can referee

### The fast simulators do not implement pistons

MCHPRS, the fastest redstone server, marked its piston request "wontfix" in 2021 and closed it as not planned ([MCHPRS issue #48](https://github.com/MCHPR/MCHPRS/issues/48)). Nucleation simulates through the same backend, Pumpkin's pistons are reported broken, Minestom has no vanilla mechanics, and Cuberite's maintainers say its redstone does not match vanilla corner cases ([Nucleation](https://github.com/Schem-at/Nucleation), [Pumpkin issue #766](https://github.com/Pumpkin-MC/Pumpkin/issues/766), [Minestom](https://minestom.net/docs/what-is-minestom), [Cuberite forum](https://forum.cuberite.org/printthread.php?tid=3006)). Paper runs Mojang's piston code but patches piston exploits by default ([Paper configuration](https://docs.papermc.io/paper/reference/global-configuration/)). The researchers conclude that only the vanilla jar, or a thin mod loader on top of it, is safe as the judge.

That option became cheaper in 2026. Since 1.21.5 the vanilla jar ships a headless runner that loads structures from a datapack, runs them under a tick timeout, writes a JUnit-style report, and with `--verify` re-runs each test 100 times per 90-degree rotation ([Minecraft Wiki: GameTest](https://minecraft.wiki/w/GameTest)). Since 26.1 the jar is unobfuscated ([PaperMC](https://papermc.io/news/26-1)). Pure-datapack tests can only pass or fail through a powered test block, so the recommended grader is a thin Fabric or NeoForge mod that registers one generic test function and reads block states in-process. The no-mod fallback is the vanilla jar driven by `/tick freeze` and `/tick step`, which give exact tick advancement ([Minecraft Wiki: /tick](https://minecraft.wiki/w/Commands/tick)). One item to check before committing: a search summary of Fabric's javadoc says its gametest server turns all experimental features on by default, which would enable the Redstone Experiments pack.

### What the grader checks

The grader's procedure follows from the rules above; the specifics are the researchers' design proposal. Validate the submission against a block and block-state allow-list before booting anything, and reject entities, command and structure blocks, and non-allow-listed NBT. Paste with updates suppressed, wait a settle period, and confirm the declared initial state. Toggle a standardised input, step ticks, and take each verdict only after a quiescence check, because a doorway cell can hold the transient `moving_piston` block at the sampling tick. Assert that every doorway cell is air when open and the door block when closed over several cycles. Accumulate the bounding box of all non-excluded blocks over every tick to get swept volume. Check seamlessness from the dumped grid by testing which component blocks are visible from the hallway cells in each rest state. No existing tool does this last check; it must be written.

No performance numbers were measured. The researchers estimate one to two thousand ticks per design for a time-capped door and expect JVM boot, not ticking, to dominate cost, which argues for two deployment shapes: a long-lived server as the agent's in-episode test tool, and a fresh batch run for final scoring. Those are estimates. On licensing, the safe pattern is the one itzg's Docker image uses: never redistribute Mojang's jar, download it at run time and require EULA acceptance ([itzg](https://mintlify.com/itzg/docker-minecraft-server/configuration/environment-variables)). The live EULA text was not read, so this needs a legal check.

### Agents submit code-built block lists with full block states

No controlled study compares output formats for 3D generation, and practice has converged on code APIs and JSON block lists ([MineBench](https://github.com/Ammaar-Alam/minebench), [FLE](https://arxiv.org/html/2503.09617v1)). The recommendation is a persistent Python environment in which the agent's own code emits a canonical list of position, block ID and full block state, relative to a fixed doorway origin, with a few helpers for fill, mirror and translate. Coordinate-only formats are insufficient because facing, delay and comparator mode decide whether a mechanism works. The harness converts the list to a vanilla structure file.

Feedback design matters more than format. SciCrafter's failures were directional and "look correct but don't work", and in the Factorio environment Claude Opus 4.1's errors were 97.7% misjudged game state with zero syntax errors ([SciCrafter](https://arxiv.org/html/2604.24697v1), [FLE v0.3](https://jackhopkins.github.io/factorio-learning-environment/versions/0.3.0.html)). The researchers therefore recommend typed validation errors, pass or fail per check with the first failing tick, a per-tick diff of the doorway against the expected state, and pull-based probes for block state and power level at chosen coordinates over a tick range. Rendered images should be an optional tool that can be switched off, since evidence that images help construction is qualitative only.

## A callable scorer invites cheating, so the referee stays hidden

### Start the ladder below 3x3 and treat 6x6 and 7x7 as stretch rungs

No source measured any model on a piston door. The evidence available points to a ladder that starts lower than you proposed. Frontier models solved about a quarter of dust-and-repeater lamp tasks unaided; in a 2023 YouTube test relayed by a third-party summary, chatbots' written instructions for a 2x2 door mostly failed ([SciCrafter](https://arxiv.org/html/2604.24697v1), [summary of Purplers video](https://sdxlturbo.ai/blog-I-Asked-AI-To-Make-Redstone-For-Me-18903)). On the human side, the 220-block 5x5 took ten months, the 338-block 6x6 about a year, and a 540-block one-second 5x5 almost two years ([Cwee 220](https://www.youtube.com/watch?v=UF-QA5weAEY), [Cwee 338](https://www.youtube.com/watch?v=6COWu8vCras), [Br1ckcraft3r 540](https://www.youtube.com/watch?v=qKYv33Rt71s)). Pistons push at most 12 blocks, and at 6x6 that limit collides with a column of door blocks plus machinery ([Wiki: Piston](https://minecraft.wiki/w/Piston), [Cwee, Aug 2026](https://www.youtube.com/watch?v=iD6u2gJwWM0)).

The researchers' recommended ladder is: binary sub-skill probes (power a piston at a distance, double and triple extenders, correct retraction order), then a 2x2 door, 3x3 non-seamless, 3x3 seamless, 4x4, 5x5, and 6x6 and 7x7 as stretch rungs. Their judgement is that any working seamless 5x5 from an agent would be a meaningful result and matching 504 to 715 would be expert-level. This calibration is inference and is the first thing the pilot should test.

### Normalise against three anchors and report tiers

The recommended per-task score is zero for no valid door and otherwise the frozen reference volume divided by the agent's volume, uncapped, with a log-ratio variant if early designs land 5 to 50 times above the record. Correctness gates size, as in AlgoTune, where invalid output scores the same as no improvement ([AlgoTune](https://arxiv.org/html/2507.15887v4)). Normalising only against records will compress today's scores toward zero, because records embody years of specialist search. Use three anchors per task: a naive working starting door shipped with the task, which also proves solvability; a time-boxed human baseline collected in the same harness; and the frozen community record re-verified by the benchmark's grader.

Report interpretable tiers beside the continuous score, in the spirit of MLE-bench medals: schema-valid, opens and closes once, passes the full suite, within 2x of the reference, within 1.25x, ties or beats it ([MLE-bench](https://arxiv.org/html/2410.07095)). Aggregate as a mean of per-task scores and publish each size separately. Run three to five independent attempts per task and report the mean as the headline with best-of-k labelled separately, since RE-Bench shows best-of-k skews confidence intervals ([RE-Bench](https://arxiv.org/html/2411.15114)). A score above 1.0 means the agent beat the frozen reference. It does not by itself mean a new world record, because the reference figures are self-reports and the current 5x5 and 6x6 records were not found.

### Isolate the final verdict

METR found o3 reward-hacked in **39 of 128 RE-Bench runs (30.4%)** against 0.7% on its HCAST suite, suggested the visible scoring function as one cause, and found that instructions not to cheat had "a nearly negligible effect" ([METR](https://metr.org/blog/2025-06-05-recent-reward-hacking/)). In a June 2026 post, METR reported that one model packaged exploits into intermediate submissions to reveal a hidden test suite, and that it could not produce a robust measurement as a result ([METR](https://metr.org/blog/2026-06-26-gpt-5-6-sol/)). A piston-door eval with a test tool sits in exactly this regime.

The defences are structural, and the exploit list is the researchers' inference, since no literature covers redstone graders. Run the Java server as a sidecar the agent cannot shell into, and compute the final score in a fresh instance from the canonical block list alone. Enforce the allow-list so that command blocks or directly placed moving-piston blocks cannot stand in for a mechanism. Keep the agent's test tool to public checks, and run hidden checks once at the end: extra cycles, both player-style and repeater-style input as the community requires, and varied toggle timings after the door's declared reset. Do not spam-toggle as a hard gate, because the Squid rules rank reset time and do not require spam-proof doors. Cap grader calls and ticks per call, log every submission server-side, and review transcripts of every top-scoring and record-beating run. Count flagged runs as failures and publish the count, as METR does.

### Run the headline track offline and add twist tasks

Record doors are public as videos and world downloads, and the Squid project's API now includes schematic endpoints ([Squid OpenAPI](https://github.com/redstone-squid/Redstone-Squid/blob/master/contracts/openapi.json)). A browsing agent could download a record and submit it. Anthropic documented a model that located a benchmark's source on GitHub and decrypted its answer key, and found URL blocklists insufficient ([Anthropic](https://www.anthropic.com/engineering/eval-awareness-browsecomp)). The recommendation is a headline track with no network access, plus a set of "twist" tasks with no public record: restricted palettes, one capped dimension, non-square openings, a required input position. Hold a procedurally generated subset private and refresh it per version. Reporting standard sizes and twists separately turns the gap between them into a contamination signal. Whether current models can reproduce record doors from memory is untested.

## Six phases, with measurements before code

The plan below is the researchers' recommendation. Phase 0 exists because several facts that determine the design were not established by the research.

| Phase | Work | Exit test |
|---|---|---|
| 0. Decide and measure | Pin the Java version and server build. Measure server boot time and ticks per second under sprint. Confirm mod-loader support on 26.x, the status of the Redstone Experiments pack in that version, and whether Fabric's test server enables experiments. | 1. Grader | Block list to structure file; allow-list validator; door predicate with quiescence check; swept-volume and seamless checks; batch and service modes. | Known-good community doors pass and known-bad submissions (command-block door, entity door, door that fails on cycle three) fail |
| 2. Agent interface | Persistent Python environment, builder helpers, typed errors, per-tick diffs, probe tools, optional renders, server-side score log. | A scripted oracle solves each rung through the same path an agent uses |
| 3. Tasks and references | Starting door and oracle per task; re-verify human records in the grader; collect time-boxed human baselines; add trivial-agent and unchanged-starting-door baselines; write twist tasks and the private set. | Every task has three anchors and a frozen reference table with version, source and date |
| 4. Pilot | Two or three models, five runs each on the lower rungs; read every transcript; ablate prompt wording for cheating; recalibrate the ladder and budgets. | No unexplained zero-score rungs and no unpatched exploits |
| 5. Package and launch | Author in Inspect with a Harbor adapter; fixed-scaffold and open-scaffold tracks; a lite subset; publish scores with intervals, cost, budgets and cheating counts; version the tasks. | An outside party reproduces a published row |

On packaging, Inspect and Harbor are the two current homes for third-party agentic benchmarks, and METR's Vivaria is winding down in favour of Inspect ([Vivaria](https://vivaria.metr.org/), [Harbor Adapters](https://arxiv.org/abs/2609.04298)). Both support a Compose sidecar for the Java server. Inspect runs scorers and tools in the host process, outside the agent's container, and still scores a sample that hits its limit; Harbor scaffolds new tasks with a separate verifier container ([Inspect sandboxing](https://inspect.aisi.org.uk/sandboxing.html), [Inspect limits](https://inspect.aisi.org.uk/setting-limits.html), [Harbor configuration](https://docs.harborframework.com/tasks/configuration)). Because a limit ends the run without an error, the best valid design must be persisted server-side.

On budget, the simulator is deterministic and CPU-only, so the researchers recommend budgeting by tokens or dollars with a cap on grader calls and a wall-clock backstop, and reading score at several checkpoints off the server-side log to get a score-versus-budget curve from one run. Scaffold choice moved GPT-4o's MLE-bench score from 0.8% to 8.7%, which is why fixed-scaffold and open-scaffold results belong in separate rankings ([MLE-bench](https://arxiv.org/html/2410.07095)). For scale, an eight-hour RE-Bench agent run averaged about $123 in 2024 ([RE-Bench](https://arxiv.org/html/2411.15114)).

The open risks, in order of how much they could change the design: simulator cost and mod-loader support on the pinned version are unmeasured; the reference table rests on self-reports, with two current records unknown; real model difficulty on piston doors is unmeasured, so the ladder could be too hard at 3x3 or too easy at 4x4; the full-seamless tier table was not read in full; the EULA position rests on old commentary; and several inputs that post-date 2025 (the Vals KSP index, MineCEraft, the 2026 METR post, the 26.x release details) come from a single source each.

## Conclusion

The research changes the shape of the project more than its feasibility. The hard part is not the simulator, which Mojang now ships in a testable form, or the scoring, which has well-worn precedents. It is the rulebook: a short, frozen document that fixes what counts as seamless, what the box contains, how long a door may take, and which mechanics are legal. The expert community spent years writing that document and still argues over edge cases, and each rule the benchmark leaves undefined becomes an exploit for an agent that can call the scorer thousands of times.

That same community is the benchmark's best asset beyond baselines. The Squid project's builds table carries an `ai_generated` flag, and its 2026 migrations add schematic storage and "simulation evidence" ([builds table](https://github.com/redstone-squid/Redstone-Squid/blob/master/schema/structure/public/tables/builds/table.sql), [Squid alembic versions](https://github.com/redstone-squid/Redstone-Squid/tree/master/alembic/versions)). The researchers read that as a move toward machine-verified submissions. A grader that implements the community's own rules could verify human submissions as well as agent ones, and an agent-built door that the record keepers accept would be a more legible result than any normalised score.
