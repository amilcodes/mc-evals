# Formalizing, compiling, simulating and auto-designing Minecraft redstone (with pistons): prior work and an IR for piston-door search

Scope note: researched 2026-11-16 for Java Edition 26.3. Sources were fetched where linked. Anything marked **[unverified / background]** comes from general community knowledge and could not be confirmed with a fetched source this session. Treat it as a hypothesis to check.

## 1. Verilog/HDL-to-redstone compilers: what they support, and do any handle pistons or timing-critical sequencing?

### Takeaway
Every HDL-to-redstone flow I found has the same shape. Yosys does logic synthesis, then a tool places and routes a cell library of dust, torches, repeaters and blocks. None of them model pistons, and none do timing-driven sequencing. Most target combinational logic and treat timing as an afterthought, if at all. "RTL2MC" could not be found and may not exist under that name.

### Cited Findings
- **Dewey (Quan Nguyen, 2018)** is a C place-and-route tool and the port of the earlier PERSHING. It reads BLIF produced by Yosys (`abc -liberty quan.lib`). It outputs a PNG plus `extraction.yaml`, "a file containing the grid of blocks to be placed," which a Python 2.7 `inserter.py` writes into a Java world. It uses a maze router. The README says "It's possible for a design to have no feasible routing -- Dewey cannot determine this, and may run forever." The README never mentions timing, delay or pistons, and gives no Minecraft version — [qmn/dewey](https://github.com/qmn/dewey); paper PDF at [nguyen_dewey_2018.pdf](https://www.ocf.berkeley.edu/~qmn/assets/nguyen_dewey_2018.pdf). The PDF could not be text-extracted this session, so its claims about placement and annealing are unverified. The README only compares parallel placement to PARSEC `canneal`.
- **MinecraftHDL (itsFrank)** is "A Verilog synthesis flow for Minecraft redstone circuits." Hacker News commenters say it does not support sequential logic (no flip-flops) and "doesn't consider timing at all." These may describe an older version — [HN thread](https://hn.nuxt.dev/item/45763877); [repo mirror](https://hn.jakechampion.name/reader/https://github.com/itsFrank/MinecraftHDL).
- **V2MC (Kenny2github)** is a Python tool that uses Yosys for elaboration and tech mapping. It emits a structure file and aims to synthesize "all synthesizable Verilog, including sequential logic." Its README caps bit width at 31 because of signal-strength limits — [awesome.ecosyste.ms entry](https://awesome.ecosyste.ms/projects/github.com%2Fkenny2github%2Fv2mc); [relatedrepos](https://relatedrepos.com/gh/Kenny2github/V2MC).
- Other flows: **RHDL** (VHDL to redstone NBT structures) — [bradeneverson.github.io](https://bradeneverson.github.io/proj/rhdl.html). **LogicLoom** (a mod that builds Verilog-2001 designs via Yosys) — [Modrinth](https://modrinth.com/mod/logicloom). **VLSI Craft** ("translate simple Verilog programs into Minecraft logic gates and wires") — [Disasm/vlsi-craft](https://github.com/Disasm/vlsi-craft). Also **FmcPGA** — [Gralerfics/FmcPGA](https://github.com/Gralerfics/FmcPGA) and **FabricHDL** — [mirror](https://github.imc.re/MinecraftMachina/FabricHDL) (I did not inspect either).
- **"RTL2MC":** two searches found nothing under this name, so its existence is unconfirmed — [search context: V2MC/MinecraftHDL results only](https://awesome.ecosyste.ms/projects/github.com%2Fkenny2github%2Fv2mc).
- **SAT-based redstone synthesis (alloc.dev, Jan 2026)** encodes each cell as boolean variables (block, dust or torch, plus power) and encodes each truth-table row as a parallel "state." It adds an 8-bit acyclic-ID constraint because otherwise "the solver produced latches." It supports dust, torches and solid blocks only. There are no pistons or repeaters and no timing model. Results: an XOR in a 6×7 area and a 150-block (10×15) one-wide full adder — [alloc.dev](https://alloc.dev/2026/01/09/redstone_from_sat).

### Inferences
- The friend's pipeline (Verilog → Verilator → Minecraft IR) has no precedent for pistons. All existing flows stop at combinational, or at most simple clocked, logic. Verilator itself is a cycle-based RTL simulator, so it abstracts away exactly the gametick, in-tick-ordering and geometry effects that decide whether a door jams.
- The SAT approach is the most relevant precedent for *size-minimal* design. Its "parallel states" trick (one copy of dynamic variables per scenario, shared layout variables) extends naturally to "one copy per gametick," which gives bounded model checking of a door over T ticks. Its acyclicity hack shows the main SAT pitfall: unconstrained solvers exploit feedback in ways the designer didn't intend. A piston-aware version would exploit update-order quirks the same way, which is desirable for records but needs ground-truth validation.

### Gaps
- Dewey paper content (cell library, placement algorithm, results) could not be extracted from the PDF.
- RTL2MC is unconfirmed. If the previous analysis cited it, ask for the URL.
- I found no HDL flow that emits pistons, observers or note blocks, or that does timing closure in gameticks.

## 2. Fast simulators and compilers: MCHPRS/Redpiler, WorldEdit/Carpet, headless Java-accurate simulation

### Takeaway
MCHPRS's Redpiler is a graph compiler for *stationary* redstone. Its node identification covers repeaters, comparators, torches, buttons, lamps, levers, pressure plates, wire and comparator-readable containers. Pistons and observers are not in its supported set. It also targets 1.20.4, not 26.3. For piston doors, the only Java-26.3-accurate "simulator" I found is the vanilla server itself, stepped tick by tick. RedstoneBench does exactly that over RCON.

### Cited Findings
- **MCHPRS** is "A multithreaded Minecraft server built for redstone." It targets **Minecraft 1.20.4**, and "Each 512x512 plot runs on a separate thread." While Redpiler runs, "all redstone connections are pre-computed, thus interaction with the world is limited." "Placing or breaking blocks while redpiler is running will cause a reset and disable redpiler." The `--optimize` flag carries the warning "This can, and will, break the state of your build." `/rtps` default is 10, and the README notes "There are two game ticks per redstone tick" — [MCHPR/MCHPRS](https://github.com/MCHPR/MCHPRS).
- **Redpiler internals:** `IdentifyNodes` creates a node "If a block is a Repeater, Comparator, Torch, Stone Button, Lamp, Lever, Stone Pressure Plate." Redstone wire is added only when an optimization flag is unset. Constant nodes are barrels, furnaces, hoppers, cauldrons, composters and cake. Trapdoors and lamps are outputs. "High-Signal Strength logic... Redpiler does not support." Pistons, observers and note blocks do not appear in the doc. The passes are ClampWeights, DedupLinks, ConstantFold ("Nodes with pending ticks are not folded"), UnreachableOutput, SSSetAnalysis, ConstantCoalesce, Coalesce and PruneOrphans. The backend is "Direct," with no JIT, and uses "a rotating queue of queues" scheduler — [Redpiler.md](https://github.com/MCHPR/MCHPRS/blob/master/docs/Redpiler.md).
- **Vanilla as simulator:** RedstoneBench's judge is a "real vanilla Minecraft Java 26.3 server," driven "tick by tick" over RCON. "Nothing is judged by a model" — [adamholter/redstone-bench](https://github.com/adamholter/redstone-bench).
- **`/tick` command** (added in 23w43a, 1.20.3) gives vanilla freeze, step and sprint control, which is what makes headless tick-stepping practical — [minecraft.wiki/w/Tick](https://minecraft.wiki/w/Tick).

### Inferences
- An industrial-strength piston-door search needs either (a) a custom piston-aware simulator, validated differentially against vanilla 26.3, or (b) vanilla in the loop as an oracle, which is slow (≈20 tps unless sprinted). Use (a) for the inner loop and (b) for acceptance.
- Redpiler's design shows *why* pistons are excluded. It compiles a static connectivity graph, and pistons rewrite that graph at runtime by moving blocks: conductors, wire supports, and the pistons themselves. Any compiled approach for doors needs a "geometry epoch" model, recompiling or switching graph variants whenever a block moves.

### Gaps
- **[unverified / background]** Carpet mod (gnembon) has historically offered tick-warp and freeze, update-suppression and "instant" options, and the Scarpet scripting language. WorldEdit and Litematica handle schematic I/O. I could not confirm 26.3-compatible Carpet builds this session.
- I found no standalone headless, Java-accurate, piston-capable simulator (outside the server jar) this session. I have no evidence for or against an MCHPRS fork with pistons. Check the MCHPRS issue tracker and Discord.

## 3. Formal semantics of redstone, and the mechanics that break simple models

### Takeaway
The only formal-verification project found, redstone-verify, proves *steady-state, acyclic, combinational* equivalence to a Verilog spec in Lean 4 + SAT/LRAT. Its own README says timing "is not proved in general," and it never mentions pistons. That confirms the previous analysis's characterization. Real piston behavior depends on the order of tick phases, block-event queueing, scheduled-tick priorities, wire update order (which changes under the experimental data pack), and the moving_piston lifecycle. None of these are visible to a steady-state model.

### Cited Findings
- **redstone-verify (formalized-si):** it accepts a layout only with "a machine-checkable argument" that it "computes its Verilog specification, for every input." The pipeline is Yosys SAT → Tseitin CNF → CaDiCaL LRAT, checked by an RUP checker and `cake_lpr`, plus a Lean 4 (4.33.1) theorem `Implements` and two-backend co-simulation. Coverage: "43 circuits: gates, adders up to 15 bits, comparators, multipliers, ALUs, wide buses." From the README: "The proof covers the steady state of acyclic layouts in the modelled subset." "Timing is measured by co-simulation and, for small circuits, by an exact tick model in Lean; it is not proved in general." "Sequential circuits are limited to three small examples." The authors report "7 wrong acceptances" found in self-audit, now fixed. Layouts are "certified, not record-setting." The manuscript is a preprint under review, and "Most of the code was written with AI assistance." Pistons are not mentioned — [formalized-si/redstone-verify](https://github.com/formalized-si/redstone-verify).
- **Java tick phase order (per dimension):** … scheduled block ticks → scheduled fluid ticks → raids → chunk ticks/random ticks → send block changes → POI → unload chunks → **execute block events** → dragon fight → entities → **block entities** → game events — [minecraft.wiki/w/Tick](https://minecraft.wiki/w/Tick).
- **Scheduled-tick priorities (Java):** seven values from −3 to 3, where lower runs earlier, and "no block … ever schedules a tick with a priority value higher than 0." Repeaters use −1 when off and −2 when on, and some repeater/comparator-in-front cases reach −3. Comparators use 0, or −1 with a repeater or comparator in front. Within a priority, ties break by scheduling order — [minecraft.wiki/w/Tick](https://minecraft.wiki/w/Tick).
- **"Redstone tick" is not an engine unit in Java:** "There is no 'redstone tick' hard-coded unit in the game's engine." Also, "no components are strictly tied to a mandatory alignment of 2-game-tick increments." Bedrock's 2-gt redstone tick with P/C ticks is Bedrock-only — [minecraft.wiki/w/Tick](https://minecraft.wiki/w/Tick).
- **Piston as block events:** extension and retraction are block events with IDs 0 and 1, run in the block-event phase — [wiki.vg Block Actions](https://wiki.vg/Block_Actions); [Piston (wiki mirror)](https://breezewiki.discard.no/minecraft/wiki/Piston).
- **Duration:** extension and retraction each take 2 game ticks (0.1 s). In Java, retraction *starts* immediately, while Bedrock may wait 1 tick depending on powering. In Java, a pulse shorter than 3 gt makes the piston "finish extending early and start retracting," which is the mechanism behind 0-tick behavior and sticky-piston block dropping ("spitting") — [Piston (wiki mirror)](https://breezewiki.discard.no/minecraft/wiki/Piston); [wiki.ronlab mirror, 2025-11 snapshot](https://wiki.ronlab.site/content/minecraftwiki_en_all_maxi_2025-11/Piston).
- **moving_piston (old "block 36") block entity:** `progress` starts at 0.0 and "increments by 0.5 each tick, including the tick on which moving the piston is created." At the start of a tick, if progress is "1.0 or higher," the block becomes its stored blockState. The other fields are `extending`, `facing` (0–5) and `source`. In Java, a head without support is removed on a "shape update from behind" — [minecraft.wiki Piston/Technical components](https://minecraft.wiki/w/Piston/Technical_components).
- **Disputed numbers ("2 gt vs 3 gt"):** community sources disagree. One Reddit tester measured 3 gt each way. Another source says 2 gt of movement, with the block not re-pushable until 3 gt — [Reddit r/redstone (mirror)](https://redlib.hbubli.cc/r/redstone/comments/15vpk6m/how_do_pistons_work_exactly_after_some_experiment); [blog](https://bryantchimplas56.blogspot.com/2022/03/minecraft-everything-you-need-to-know.html). Wiki: 2 gt. The likely reconciliation (inference): 2 gt of block-entity progress, plus the 1-gt offset between the block-event phase (where the move starts) and the next tick's block-entity phase, makes "available as a solid block" land at 3 gt after the power change in many setups.
- **Redstone Experiments (version-specific):** added 24w33a (1.21.2) as an *experimental data pack*, and per the wiki still not default as of the page that lists 26.3 as latest. Changes: wires closer to a signal change update first. Junction order is front, then left, then right (since 24w34a; left over right). Order is "randomized once per circuit" when there is no context. Wires no longer respond to neighbor updates from other wires. The wiki gallery shows that *which of two pistons extends* depends on the lever's directional update order, on repeater tick priority, and on powered rails updating a piston early — [minecraft.wiki/w/Redstone_Experiments](https://minecraft.wiki/w/Redstone_Experiments); [24w33a notes](https://www.minecraft.net/en-us/article/minecraft-snapshot-24w33a).
- **Turing-completeness:** commonly asserted ("it has long been known that Minecraft… is Turing complete") but I found no formal NP- or PSPACE-hardness paper specific to redstone or pistons — [Haupz blog](https://blog.haupz.de/meta-minecraft.html).

### Inferences
- A correct piston model must be at least a **discrete-event model with in-tick ordering**. Each gametick is a sequence of phases. The scheduled-tick phase is a priority queue ordered by (time, priority, insertion order). The block-event phase is a FIFO, and **[unverified / background]** events added during that phase are processed in the same tick. Block-entity ticks drive moving_piston progress. Neighbor and shape updates are DFS-like cascades with location-dependent order.
- Mechanics that break "gates + delays" models: (1) **quasi-connectivity**, where pistons are powered by conditions at the block above, but only re-check on a block update **[unverified / background; standard wiki content not fetched this session]**. (2) **BUD/update-order dependence**. (3) **0-tick and short pulses** (<3 gt), which cause instant completion and block dropping. (4) **pushability and immovables**, including the 12-block push limit **[background]**, and the fact that moving_piston blocks and extended pistons are immovable mid-motion. (5) **self-modifying geometry**: pushing a conductor, dust support or observer changes the circuit itself. (6) **observers**, which fire on state changes, including those caused by moved blocks, with a 2-gt-long pulse after a 2-gt delay **[background]**. (7) **Experimental wire ordering** and directional (location-hashed) update orders.
- Practical consequence: "two controllers with identical final outputs, one of which jams" is not just plausible but expected. Any equivalence notion for doors must be **trace equivalence over the full tick-by-tick world state**, including intermediate geometry, not output equivalence at steady state.

### Gaps
- I did not fetch an authoritative source for exact observer timings, the quasi-connectivity rules text, or same-tick block-event re-queue semantics. Check minecraft.wiki "Piston", "Observer", "Block event", and decompiled 26.3 `Level.blockEvent` / `PistonBaseBlock.triggerEvent`.
- I found no evidence of 26.x changes to piston mechanics, but no 26.x changelog was fetched. Diff the 26.3 piston and redstone code against 1.21.x before trusting older community lore.
- No peer-reviewed formal semantics of redstone with pistons was found.

- **Categories in popular coverage:** seamless (no redstone or pistons visible) vs non-seamless, and "layout size" doors that fit all redstone within the piston layout volume — [Sportskeeda](https://www.sportskeeda.com/minecraft/minecraft-redditor-makes-hidden-piston-door). ### Inferences
- **[unverified / background]** In the record community, opening and closing times are usually stated in gameticks from input to a fully open (passable) or fully closed (flush/seamless) state. Records are tracked separately per size, pattern and restriction, and per version (Java vs Bedrock). Common record techniques are 0-ticking and block-dropping sticky pistons, observer-based BUD and pulse logic, slime/honey "stacking" and flying-machine-like sub-assemblies, quasi-connectivity powering to save wiring, "wire-less" designs where pistons push their own power sources, and exploiting update order (directional/location-dependent). The search IR must be able to express all of these, or the search will never reach record territory.
- The volume metric (bounding box including all redstone, excluding input) means the search objective is exactly "min bounding-box volume subject to correct open and close traces, tie-break total gt."

## 5. Automated redstone design: GA/RL, procedural generation, LLMs, "redstone synthesis"

### Takeaway
Automated redstone design is nascent. The work so far is LLM benchmarks (RedstoneBench, with piston doors on vanilla 26.3; SciCrafter, where lamp-pattern tasks plateau at about 26% for frontier models), SAT synthesis of small combinational gates, and evolutionary work on *moving machines* (EvoCraft, MAP-Elites flying machines) that did not target logic. Nothing I found does search-based synthesis of piston doors.

### Cited Findings
- **RedstoneBench:** 16 tasks in five families: Door (2×2/3×3/4×4), Mechanical (extend a block 2 or 3 up), Logic, Memory and Timing (20- and 120-tick clocks, a 30-tick pulse). Answers are built on a vanilla Java 26.3 server via RCON and stepped tick by tick. Scored by bounding-box volume, ties broken by ticks. MIT-licensed, 5 stars. The README shows no scores (a leaderboard is referenced but not on the README) — [adamholter/redstone-bench](https://github.com/adamholter/redstone-bench).
- **SciCrafter (arXiv 2604.24697):** "Can Current Agents Close the Discovery-to-Application Gap? A Case Study in Minecraft" (Zhou et al.; v1 2026-04-27, v2 2026-05-20). Its tasks are parameterized redstone tasks that light lamps in simultaneous or timed patterns. GPT-5.2, Gemini-3-Pro and Claude-Opus-4.5 "all plateau at approximately 26% success rate." Knowledge *application* is the largest gap. Pistons are not mentioned in the abstract — [arXiv](https://arxiv.org/abs/2604.24697).
- **EvoCraft (2020):** a Minecraft mod plus Python API for open-ended evolution. Evolution grows target structures easily, but "is unable to find a solution when rewarded for creating such machines" (moving machines) — [arXiv 2012.04751](https://arxiv.org/pdf/2012.04751).
- **Evolving Flying Machines (GECCO 2023):** MAP-Elites (quality diversity) finds perpetually moving slime/piston machines far more reliably than fitness-only evolution, with a best configuration at 93.33% success — [arXiv 2302.00782](https://arxiv.org/pdf/2302.00782).
- **SAT redstone (2026):** see §1 — [alloc.dev](https://alloc.dev/2026/01/09/redstone_from_sat).
- Off-target: "Generating Redstone Style Cities" evolves building layouts, not circuits — [arXiv 2307.09777](https://arxiv.org/pdf/2307.09777).

### Inferences
- The evolution results warn that raw fitness search over block grids fails on *moving* mechanisms. Diversity (MAP-Elites over descriptors such as volume, open time and close time) and structured representations help. For doors, a natural MAP-Elites grid is (volume bin × opening-gt bin), which directly produces a Pareto front.
- LLM-only design is unlikely to reach records given the ~26% plateau on simpler lamp tasks. An LLM is better used as a proposal operator inside a verified search loop.

### Gaps
- I found no RL-for-redstone papers and no Voyager/MineDojo work targeting circuits. Those systems focus on survival skills, and I did not fetch them this session.
- RedstoneBench leaderboard numbers are not on the README.

## 6. IRs for moving blocks (hybrid mechanical/logic) and PLC sequencing analogues; recommended IR and search loop

### Takeaway
No existing redstone tool has a hybrid mechanical/logic IR. The right abstraction is a **timed, ordered event schedule over a mutable voxel state**: actions are piston block events with gametick timestamps *and* in-tick order, and their guards are geometric preconditions. That is a timed-automaton or Petri-net style model, analogous to SFC/GRAFCET in PLC design. Verilog/Verilator should not be the primary IR. At most, they can be one way to describe the *controller* after the motion schedule is fixed.

### Cited Findings
- The facts that force this design are all cited above. Pistons act through block events in a dedicated tick phase ([Tick](https://minecraft.wiki/w/Tick); [wiki.vg](https://wiki.vg/Block_Actions)). Moving blocks exist as moving_piston entities for about 2 gt ([Technical components](https://minecraft.wiki/w/Piston/Technical_components)). Short pulses change outcomes ([Piston mirror](https://breezewiki.discard.no/minecraft/wiki/Piston)). Which piston fires can depend on update order ([Redstone Experiments](https://minecraft.wiki/w/Redstone_Experiments)). Compiled static-graph simulators exclude pistons ([Redpiler.md](https://github.com/MCHPR/MCHPRS/blob/master/docs/Redpiler.md)), and steady-state proofs exclude timing ([redstone-verify](https://github.com/formalized-si/redstone-verify)).
- **[unverified / background — standard references, not fetched this session]** IEC 61131-3 defines Sequential Function Chart (SFC) for PLCs as steps, transitions with guard conditions, and actions with qualifiers (N, S, R, P, D for time-delayed, L for time-limited). GRAFCET (IEC 60848) is its specification-level ancestor. Ladder logic is combinational/latching rung logic and is poor at expressing sequences, which is why SFC exists. Timed automata (UPPAAL) and time Petri nets are the standard formal models for "actuator A must finish before B starts" interlocks. Industrial practice verifies these interlocks by model checking or by simulation against a plant model.

### Inferences (concrete opinion)
**Why "Verilog → Verilator → MC IR" is the wrong spine:** Verilog semantics assume fixed wiring and clocked or combinational evaluation. A piston door's essence is *choreography of shared, mutable geometry*: pushed blocks, piston heads and moving_piston entities occupy cells, block other pistons, and carry or break power paths. Verilator would certify the controller's output waveform, but the jam happens in the plant. That is exactly the "same outputs, one jams" failure mode. Verilog is fine as an optional front end for the *controller* once timing constraints exist. It is not the design IR.

**Recommended three-layer IR:**
1. **Plant / motion layer ("Motion Schedule IR")**
   - **State:** a sparse voxel map, where each cell holds a block kind plus attributes: movable (normal), sticky-movable, immovable, destroy-on-push, slime/honey, conductor, transparent, and occupied-by-moving_piston.
   - **Actuators:** each piston has a position, a facing, sticky or non-sticky, and its current state (retracted, extending(k), extended, retracting(k)).
   - **Actions:** `Extend(p, t, ord)` and `Retract(p, t, ord, pulse_len)`, where `t` is the gametick and `ord` the block-event index within the tick. `pulse_len < 3` marks a 0-tick/drop retraction. Each action has a *pushability precondition*: push-limit check, no immovables in the push path, and the target cell free or becoming free by `t`.
   - **Goal predicates:** `Open(t)` holds when the doorway cells are air or passable. `Closed(t)` holds when they match the frame pattern and the flush/seamless predicate on visible faces.
   - This layer alone is a timed planning problem, similar to sliding-block puzzles with timing. It can be searched *first*, independent of redstone: find the shortest-makespan schedule of piston actions that takes Closed to Open and back, using the fewest pistons and fewest cells.
2. **Controller layer ("Timed Signal Graph")**: a Redpiler-like graph (repeaters, comparators, torches, dust, observers, QC edges and BUD edges) whose nodes emit power changes into the plant, annotated with exact delays and tick priority. It differs from Redpiler in one way: **edges are conditioned on plant geometry**. For example, "dust D exists only while block B is unmoved," and "observer O fires when cell C changes." In effect it is a guarded network that a timed automaton can represent. Its synthesis target is to *realize the motion schedule's (t, ord) sequence*, which is a scheduling and timing-closure problem.
3. **Embedding layer**: concrete coordinates and blocks in a bounding box. This is where volume is optimized, through placement and routing with shared cells, wires that pistons move, and QC powering.

**Search loop:**
- (a) Enumerate or plan motion schedules (A*/IDA* or a CP-SAT/SMT time-indexed encoding, with one copy of the dynamic voxel variables per gametick, like the "parallel states" SAT trick, bounded to T ≈ 20–60 gt).
- (b) For each schedule, synthesize controller plus embedding with SAT/SMT or MAP-Elites over (volume, open-gt, close-gt), using LLM or library "motifs" (known record sub-mechanisms) as mutation operators.
- (c) Evaluate in a **custom fast piston-aware discrete-event simulator**. It needs phases in vanilla order, a scheduled-tick priority queue, a FIFO block-event queue, and moving_piston progress of +0.5/tick. It should be **differentially tested** against vanilla.
- (d) Accept only after a **vanilla 26.3 server-in-the-loop** check via RCON and `/tick step`, as RedstoneBench does. That check should include both orientations and mirror images, because directional and location-dependent update order can make a door work in one rotation and fail in another, plus repeated open/close cycles and spam-input tests.
- Equivalence and correctness are always **full-trace** properties (no illegal states, no stuck pistons, no dropped blocks unless intended, a periodic return to Closed), never steady-state output equality.

**What to borrow:** SFC/GRAFCET semantics for authoring sequences (steps = door phases, transitions = gametick or geometric guards). UPPAAL-style timed-automata checking for "can piston A's push ever overlap piston B's moving_piston?" Redpiler's graph-pass architecture for the stationary parts of the controller. redstone-verify's certification idea, restricted to the stationary sub-circuits.
